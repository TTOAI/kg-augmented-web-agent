# 사이트별 구조 지식 그래프는 웹 에이전트에 언제 도움이 되는가

## When Does a Site-Specific Structural Knowledge Graph Help an LLM Web Agent?

---

## 요 약

LLM 기반 웹 에이전트가 같은 사이트의 페이지 구조를 매번 관측에서 재발견하는 비효율을 해소하기 위해, 사이트 구조를 사전 계산된 지식 그래프(Knowledge Graph, KG)로 외부화하고 페이지 클래스 식별자를 숨긴 최소 힌트로 주입한 V1을 KG 미사용 기준 에이전트(baseline) V0와 WebArena-Verified GitLab 7개 사전 등록 과제 × 3 시행(trial)으로 비교한다. 측정 도중 평가기의 메타데이터·답 포맷·API 엔드포인트(endpoint) 불일치(mismatch) 결함이 다수 식별되어 평가기 통과율을 KG 효과 지표로 그대로 쓸 수 없었기에 *의미적 성공률*(에이전트가 과제의 의미적 목표에 도달·완수했는지를 로그·HAR로 검증한 시행 비율)을 재정의해 비교했다. 결과: (i) **의미적 성공률은 V0=V1=6/7 (과제 단위/task-level)** 로 동일 — KG는 통과 여부를 바꾸지 않으며 이는 기준 에이전트의 LLM 능력에 좌우된다. (ii) **스텝 효율(step efficiency)** 은 의미적-성공한 6 과제 중 4 과제에서 V1이 평균 0.7~7.7 단축하며 그 중 2 과제(309, 664)는 V0의 파국적 시행(catastrophic trial)을 V1이 일관된 범위로 안정화해 표준편차를 5~12배 감소시키는 *최악 사례 안정화(worst-case stabilization)* 가 주요 메커니즘이다. (iii) **비ARIA 모달 단일 과제(568)** 는 V0/V1 모두 시간 초과(timeout) — KG의 ARIA 표준 기반 수집기가 최신(modern) 비표준 컴포넌트를 포착하지 못함이 적용 경계(boundary)로 드러난다. KG는 *스텝 효율 도구* 로 유의미한 효과를 보이지만 의미적 성공률 자체에는 영향하지 않는다.

주요어: 지식 그래프, 웹 에이전트, 사이트별 구조, 힌트 주입, 효과 조건 특성화

## 1. 서 론

LLM 기반 웹 에이전트[1, 2]는 매 서브목표마다 (1) 어느 페이지 클래스가 과제를 담당하는지, (2) 그 페이지에 어떤 필터·버튼이 있는지, (3) 어느 URL 경로가 단축인지를 관측만으로 재발견한다. 이 반복은 같은 사이트의 과제마다 누적된다.

선행 연구는 사이트 지식의 사전 자산화에 집중했다. SteP[3]은 수동 정책 스택을, WALT[4]는 역공학 도구 함수를, AWM[5]은 실행 궤적 재사용을 제공한다. 본 연구는 *사이트 구조 자체*를 KG로 외부화하고 최소 힌트로 주입한다.

본 논문은 두 질문을 묻는다. **KG는 어떤 조건에서 스텝(step)을 줄이고, 어떤 조건에서 효과가 없거나 부정적인가? 그리고 그 효과는 과제 통과율 변화로 이어지는가?** 이를 답하기 위해 본 연구는 ARIA 역할 속성·표준 폼 요소만으로 사이트 구조를 추출하는 사이트 무관(site-agnostic) KG 구축 프로토콜과, 추출된 구조를 *구조 단서 한정·구체값 미주입* 원칙(페이지 클래스·경로(path)·필터 카테고리(filter category) 같은 구조 단서만 노출하고 라벨 값·파라미터 값·텍스트 콘텐츠는 에이전트의 페이지 상호작용에 위임)으로 주입하는 최소 힌트 모드를 제시한다. 효과 가능성(H)·한계 가능성(L)·무영향 가능성(Null)의 원형(archetype) 매트릭스 적용 범위(coverage)를 기준으로 선정한 7 과제를 측정 시작 *전* 가설 카드와 함께 git에 등록해 재현성을 확보했다. 측정 도중 WebArena-Verified 평가기의 메타데이터·엄격 일치(strict-match)·엔드포인트 불일치 결함이 KG 효과를 가리는 잡음(noise)으로 작용함을 발견하여, 평가기 출력 대신 *의미적 성공률*(에이전트가 과제의 의미적 목표에 도달·완수했음을 로그·HAR로 검증한 시행 비율)을 별도 지표로 도입해 통과율과 스텝 효율을 분리 분석했다. 그 결과로 (a) 의미적 성공률은 V0=V1=6/7로 동일 — 과제 통과 여부는 기준 에이전트의 LLM 능력에 좌우됨, (b) 스텝 효율은 V1이 4 과제에서 평균 0.7~7.7 단축 + 2 과제에서 최악 사례 표준편차 5~12배 감소, (c) 비ARIA 모달이 KG 적용 경계라는 세 관찰을 보고한다.

## 2. 방 법

### 2.1 KG 구축

세 단계로 수행한다. 1단계는 출발 URL 집합에서 너비 우선 탐색으로 페이지를 수집하고 URL 규칙으로 페이지 클래스를 할당한다. 2단계는 각 클래스 샘플에서 ARIA 역할 속성(메뉴 항목, 옵션, 탭, 대화상자 팝업 트리거)과 표준 폼 요소만을 근거로 액션·필터·대화상자를 수집한다. 의도적으로 사이트에 무관하며 비표준 컴포넌트는 포착하지 않는 대신 단일 구현으로 여러 사이트에 이식된다. 3단계는 URL 템플릿, 범위, 트리거 문구, 필터 카테고리를 결합해 클래스 카탈로그를 만든다. 현 GitLab KG는 139 클래스·23 클래스의 필터 카테고리·2,731 전이 엣지를 담는다.

### 2.2 실행 시점 통합과 최소 힌트 — "구조 단서 한정·구체값 미주입"

실행 시점에서 KG는 세 모듈로 소비된다. **타겟 클래스 추론기**는 K=3 자기 일관성(self-consistency) LLM 호출로 과제에서 목표 클래스를 결정한다. **경로 탐색기**는 6단계 단계별 후퇴(cascade)로 현재 클래스에서 목표 클래스까지의 경로를 탐색한다. **힌트 생성기**는 경로 단축 URL과 현재 페이지 표면 정보(액션 카탈로그·필터 카테고리 존재)를 관측 메시지에 주입한다.

설계 원칙은 _KG는 구조적 방향만 노출하고 구체값은 에이전트가 페이지 상호작용에서 직접 찾는다_ 이다. 최소 힌트 모드(`KG_MODE=minimal`)는 (i) URL 파라미터 레시피, (ii) 페이지 클래스 식별자, (iii) 필터 카테고리의 예시 값·옵션 값·기본 값을 모두 억제한다. 이 분리는 V1의 스텝 단축이 KG의 *구조 정보 우월*에서 오는지 _KG가 정답을 흘려서_ 오는지 분리한다.

## 3. 실험 설정

WebArena-Verified GitLab 자가 호스팅 인스턴스를 사용한다. 에이전트 LLM은 OpenAI `gpt-5.4-mini` 단일 모델이다. 변종은 V0(`KG_ENABLED=0`)와 V1(`KG_ENABLED=1 KG_MODE=minimal`) 둘이며 각 (과제 × 변종) 셀(cell)에 3 시행을 측정한다. 측정 방법론은 _과제 고정 집합(fixed-set) 사전 잠금이 아니라_ 반복 회차(iterative round) + 약한 사전 등록이다. 회차 시작 전에 (a) 선정 규칙(원형 gap 기반), (b) 종료 규칙(stopping rule, 세 원형에 ≥1 과제 + 누적 과제 ≤ 8), (c) 모든 결과 보고 의무를 git에 commit한다. 본 측정은 회차 1·2 합계 **7 과제 × 2 변종 × 3 시행 = 42 시행** 이다.

### 4.2 벤치마크 평가기 결함과 의미적 성공률 재정의

WebArena-Verified 평가기 출력만으로 V0와 V1을 비교하면 KG 효과 측정이 *평가기 결함의 잡음*에 가려진다. 본 측정에서 식별한 결함 유형은 다음 셋이다.

(a) **메타데이터 불일치** (과제 102): 평가기의 기대(expected) URL이 과제 의도와 *다른 저장소*(`byteblaze/a11y-syntax-highlighting`)를 가리킨다. 에이전트는 과제가 명시한 `a11yproject/a11yproject.com` 저장소에 정확히 도달했음에도 NetworkEventEvaluator가 fail로 기록한다.

(b) **답 포맷 불일치** (과제 309): 과제는 *username* 을 묻지만 평가기 기대 값은 *email*(`wright.grayson@gmail.com`)이다. 에이전트의 username 답은 엄격 일치에서 실패한다.

(c) **API 엔드포인트 불일치** (과제 664): UI 폼 제출(`/-/issues/new`→이슈 페이지 redirect)로 이슈가 *실제 생성*(#2393)되었음에도 평가기는 REST `/api/v4/projects/{id}/issues` POST만 인정해 실패로 기록한다.

이 세 결함이 V0와 V1 모두에 동일하게 작동하므로 *KG 효과 비교 자체*는 깨지지 않으나, 평가기 통과율을 보조 지표로 쓰면 KG의 실제 영향이 가려진다. 따라서 본 절 이하에서는 **의미적 성공률**(`agent_response.json` status=SUCCESS + 로그·HAR 검증으로 과제가 명시한 의미적 목표에 도달·완수했음이 확인된 시행 비율)을 별도 지표로 채택한다.

### 4.5 인사이트 — KG 효과의 발생 조건과 메커니즘 (568 제외 6 과제)

각 과제의 효과 메커니즘을 분리해 정리한다.

**102 — 안정적 평균 단축 (다중 홉/multi-hop NAV)**. V1은 KG의 `project/issue_list` 추론과 `/-/issues` 경로 단축을 활용해 V0의 3-홉(프로젝트→Issues→라벨)을 1-홉 `goto`로 압축한다. KG는 라벨 *카테고리 존재* 만 알려주고 라벨 *값* "help wanted"는 에이전트가 과제에서 추출 → 드롭다운 직접 클릭. 양쪽 sd가 작아 효과가 시행 간 안정.

**309 — V0 검색 폭주의 차단 (단일 URL/single URL RET)**. V0 [13, 19, **54**] sd 22.1 — 54-스텝 시행은 commit 페이지·검색 박스·필터 사이를 반복 왕복하는 회로다. V1은 KG가 `project/main`으로 합의 추론해 프로젝트 메인을 닻점(anchor)으로 제시 → 행동 경로에 머물러 commit 페이지를 빠르게 식별. KG의 직접 효과는 commit 페이지 자체가 아니라 *프로젝트 닻점 제공*으로 V0의 검색 회로를 차단(prevent)하는 것이다. 단 V1 시행 1은 KG 닻점에 갇혀 재시도 소진된 *반대 사례* 도 함께 발생.

**664 — V0 폼 혼란의 차단 (issue 작성 MUT)**. V0 [12, 14, **37**] sd 13.9 — 37-스텝 시행은 폼 작성 중 다른 프로젝트로의 잘못된 이동·복귀를 반복한다. V1은 KG의 `project/issue_detail` 인접(adjacent) 안내로 *new issue* 사이드바 항목에 즉시 도달 → 폼을 한 번에 작성. 309와 동일한 "정박된 행동 경로(anchored trajectory)가 파국적 분기를 차단" 메커니즘이나 폭주 *패턴* 은 다르다 — 309는 검색 회로, 664는 폼 작성 중 분기.

**418 — 작은 양쪽 개선 (status 설정 MUT)**. KG는 `account/edit`으로 확신 추론하지만 status UI는 navbar avatar 팝오버에 위치해 정확 매핑은 아니다. 그럼에도 유용 인접(useful adjacent)으로 작용해 평균 −0.7 단축, 최악 사례 18→15. 사전 가설이었던 *능동적 오도*(시간 초과)는 발생하지 않았다.

**156 — 효과 미발생 (범위 모호 NAV)**. V0 평균 4.0 (sd 0) → V1 평균 4.7 (sd 1.2). 기준 에이전트가 이미 1-2 홉 효율적이라 KG의 단축 여지가 없으며 V1 시행 1건은 6 스텝으로 확장되어 *역효과* 경계 사례를 보인다.

**44 — 무영향 (1-스텝 직접 링크 NAV)**. V0=V1=2 스텝 (sd 0). KG가 줄 추가 구조 정보가 없는 능동적 통제(active control). 측정 도구(instrument)가 "차이 없음"을 출력할 능력을 가짐을 입증한다.

종합하면, **KG는 (i) 기준 에이전트가 파국적 분기 가능성이 있는 다중 단계(multi-step) 경로를 거치고 (ii) 목표 또는 유용 인접 클래스가 KG에 매핑되어 있을 때** 평균 단축과 최악 사례 안정화로 스텝 효율을 개선한다. **기준 에이전트가 이미 효율적인 경우 KG는 무영향이거나 작은 역효과**를 줄 수 있으며, 모든 효과는 스텝 단위에 한정되어 *의미적 성공 여부 자체는 변화시키지 않는다* — 과제 통과 능력은 기준 LLM 에이전트의 일반 추론(general reasoning) 성능에 의해 결정된다.

### 4.6 과제 568 — 비ARIA 모달의 KG 적용 한계 (별도 분석)

다른 6 과제와 달리 568은 V0/V1 모두 의미적으로 *실패* 한다. "Invite members" 다이얼로그가 GitLab Pajamas Vue 컴포넌트로 ARIA 비순응(ARIA-non-conformant)이며 KG의 `project/member_list` 클래스에 모달 내부 액션 카탈로그가 비어 있다. 두 변종 모두 모달 트리거(`Invite members` 버튼)까지는 도달하지만 모달 내부의 사용자 검색 입력·역할 선택을 처리하지 못해 3 시행 모두 20분 시간 초과한다. KG 기여는 모달 진입 *직전까지* 로 한정되며 내부에서 소멸한다. 이 한계는 KG가 ARIA 표준 기반 수집기로 빌드되어 있다는 *의도적 설계 선택*에서 기인하며, 비표준 컴포넌트가 다수인 최신 웹 프레임워크에서는 KG 적용 경계가 된다. 568은 다른 6 과제와는 *전혀 다른 패턴*(둘 다 실패, KG 도움 범위 밖)이므로 §4.5의 효과 조건 분석에서 분리해 별도 절로 보고한다.

## 5. 결론 및 향후 연구

본 연구는 OpenAI `gpt-5.4-mini` 단일 모델 위에서 WebArena-Verified GitLab의 7 과제를 V0(KG 미사용)와 V1(KG 최소 힌트 모드)로 측정해 사이트별 KG의 효과를 정직하게 특성화했다. 핵심 발견은 다음 셋이다.

(1) **스텝 효율에서 유의미한 효과**. V1은 의미적 성공한 6 과제 중 4 과제(102, 309, 418, 664)에서 평균 스텝을 0.7~7.7 단축한다. 그 중 2 과제(309, 664)는 기준 에이전트의 파국적 시행(54·37 스텝)을 V1이 일관된 범위로 안정화하여 표준편차를 5~12배 감소시키는 *최악 사례 안정화*가 효과의 주요 메커니즘이다. KG의 정박 대상(anchored target)이 기준 에이전트의 파국적 분기(검색 회로·폼 혼란)를 차단한다.

(2) **과제 성공률은 기준 에이전트 능력에 좌우**. 의미적 성공률은 V0=V1=6/7(과제 단위)로 *동일* 하다. 시행 단위에서는 V0 18/21·V1 17/21로 V1이 한 시행 낮다(309의 KG 닻점 갇힘 사례). KG는 과제가 *통과되는지 여부*가 아니라 *통과까지의 효율*에 기여하며, 의미적 성공·실패는 LLM 에이전트의 일반 추론 능력에 의해 결정된다.

(3) **비ARIA 컴포넌트가 적용 경계**. 568에서 KG는 모달 트리거 도달 직전까지만 안내하고 내부에서 기여가 소멸한다. ARIA 표준 기반 수집기의 *의도적* 한계이며 최신 웹 프레임워크에서 KG 적용 범위를 제약한다.

향후 연구 방향은 (i) **KG 재설계** — 비ARIA 컴포넌트를 직접 탐색하는 수집기 확장으로 모달·Vue 기반 widget 내부도 매핑하여 적용 경계를 넓히는 것, (ii) **다른 사이트에서의 일반화** — Reddit/Postmill 등 ARIA 준수도(conformance) 수준이 다른 사이트에서 동일 KG 구축 프로토콜이 사이트 무관하게 작동하는지 교차 사이트(cross-site) 측정으로 실증하는 것, (iii) **성공률 측면 기여 가능성** — KG가 스텝 효율을 넘어 답 포맷·HTTP 요청 패턴까지 가이드하면 의미적 성공률 자체에도 기여할 수 있는지 — 본 연구가 스텝 효율 효과는 실증했지만 통과율 기여는 *시도되지 않은 차원* 으로 남았다 — 를 조사하는 것이다.

한계. N=7 과제·단일 사이트(GitLab)·단일 모델·반복 회차 선정으로 일반화는 제한적이며, 평가기 메타데이터·엄격 일치 결함이 KG 효과 측정의 외부 잡음으로 작용한다.
