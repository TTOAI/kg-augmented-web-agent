# L1: task 418 — KG 미매핑 영역에서 능동적 오도 (MUT)

**Type**: MUTATE
**Source**: WebArena-Verified task 418
**Round**: 1 (Round 0 pilot에서 task 411의 L1 가설이 refuted된 뒤 새로 선정)

## Intent
> Set my gitlab status as Busy.

Start URL: `http://localhost:8023`

## Hypothesis
GitLab의 사용자 status 설정 UI는 navbar 우측 avatar의 popover 안에 있다. 이 컴포넌트는 Vue 기반 비ARIA로 구현되어 있고, KG의 클래스 카탈로그·액션 카탈로그 모두 status 매핑이 0건이다 (phase 0 grep 검증됨).

KG 타겟 클래스 추론기는 후보 집합 강제 추론 구조라 status 매핑 부재를 인지하지 못하고 차선 후보 — 가장 가능성 높은 건 `account/edit` 또는 `account/account` (일반 profile/settings) — 를 confident하게 선택. KG 에이전트는 그 잘못된 target을 신뢰해 settings 페이지로 진입, "status" 입력란을 검색하지만 발견 실패 → 반복 재시도 후 navbar avatar로 우회. baseline는 KG 안내 없이 navbar의 avatar 자체를 직접 탐색해 popover 진입이 비교적 짧음.

## Predicted baseline
- step 1~2: dashboard 페이지에서 우측 상단 avatar (Byte Blaze) 인지 후 클릭.
- step 3: popover 열림, "Set status" 항목 발견 후 클릭.
- step 4: status 입력 dialog 열림 → "Busy" 선택 또는 입력.
- step 5: submit → report_success.
- 예상 step 수: 5~7

## Predicted KG
- step 1: KG 추론기가 `account/edit` (또는 동등) confident routing.
- step 2~5: 에이전트가 settings 페이지 (e.g., /-/profile) 진입 후 status 입력 검색 → 발견 실패.
- step 6~10: 다른 settings sub-page (preferences, notifications, account 등) 탐색 후 모두 실패.
- step 11~N: 결국 navbar avatar로 회귀, popover 진입, status 설정 후 submit.
- 예상 step 수: 12~25 또는 budget exceed (`MAX_STEPS_PER_TASK=60`)

KG이 baseline보다 *훨씬 길다*면 active misdirection 가설 확증.

## Mechanism invocation signal (KG log)
- `[KG] inferred target=account/<something>` (`status` 미포함, 가장 likely는 `account/edit` / `account/account` / `account/preferences`)
- agent thought에 settings 페이지에서 "status" 검색 흔적
- HAR에 `/-/profile`, `/-/profile/preferences` 등 settings URL 반복 GET
- 후반부에 navbar avatar (Byte Blaze) 클릭 흔적

## Falsification criterion
- KG step 수가 baseline와 *동등하거나 적음* (KG가 도움 또는 무영향)
- KG 추론기가 status를 (간접적으로라도) 정확히 인지 — 예를 들어 user/profile 같은 클래스 안내 후 agent가 거기서 popover 추론
- agent가 settings 페이지를 거치지 않고 baseline와 동일하게 navbar avatar 직행

→ 위 중 하나라도 성립하면 본 task에서 L1 active misdirection 가설 refuted (정직하게 보고).
